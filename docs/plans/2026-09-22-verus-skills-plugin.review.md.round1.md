## Section notes

### 1. Architecture

Component boundaries are right: the root is derived from `import.meta.url` in both installs, the hook is the only component that needs `CLAUDE_PLUGIN_ROOT`, and the pointer file is a one-way, best-effort channel with the existing symlink branches as fallback. The single point of failure is the locator, and it is broken — see the P0. The second structural weakness is the pointer's freshness: it is refreshed only on `startup|clear|compact`, so a `claude plugin update` mid-session leaves a pointer into a removed `<version>` cache directory, and under a plugin install there are no symlink branches to fall through to; the plan degrades correctly (empty `SKILLS_REPO` → "distro root not found" → the skill asks the user) but never says so. Security boundary: `vendor-node/` is executable third-party code committed into the repo and re-downloaded without integrity verification — the one genuinely new trust edge this plan creates, and the one it does not guard. New artifacts (the plugin, the marketplace, the hook package, the vendored SDK) all have a build/publish story via `make release` + `claude plugin tag`, except that nothing pushes. A diagram is not needed; the spec's §4.3 data-flow block is sufficient and the plan's Architecture paragraph reproduces it accurately.

### 2. Code quality

Module organization is sound and matches the repo's conventions (ESM, exported pure functions plus a guarded `main()`, the `process.argv[1]` self-check). The locator snippet is duplicated three times across markdown with only the skill name differing — genuinely unavoidable, since each skill's fenced block is its own shell call, and the plan does the right thing by pinning the duplication with a test that compares the three after substitution. DRY violations worth naming: the ten-skill list is hard-coded in `tests/plugin.test.mjs` while `skillDirs()` already computes it; the full `hooks` object is duplicated verbatim between `hooks/hooks.json` and `.codex-plugin/plugin.json` (pinned by `deepEqual`, acceptable). Missing edge cases: pointer file that exists but is empty or contains a relative path (the `[ -n "$c" ]` and `-f` guards cover both, untested); plugin installed on top of symlinks (P2 above); `package-lock.json` version drift (P1 above). Touched docs: the README rewrite is accurate against the current file, all six Task 7 anchor strings were verified verbatim in their source files, and `USING.md` does have the `## Rules` heading Step 8 targets. The SDD DOT diagram is the only doc artifact left behind.

### 3. Tests

Framework detection is correct: `node --test tests/*.test.mjs` via `npm test`, `node:assert/strict`, `mkdtempSync` + `after()` cleanup, `tests/fixtures/fake-bin` stubs — the plan follows every existing idiom, and the "107 existing + 6 new" count in Task 1 Step 8 checks out (15+14+5+24+1+18+30 = 107). Coverage per feature: **vendored SDK** — the resolution fallback, the only path that matters in production, is not actually exercised (P1 #3); add `test("loadSdk resolves the vendored copy when node_modules is absent")` spawning `node -e` against the copied judge, expecting stdout `function`. **Judge hard failure** — the planned test cannot pass (P0 #2). **Pointer file** — well covered, including the unwritable-`$HOME` path, except for the root-uid case. **Locator** — covers pointer hit, dead pointer, fall-through to `.claude`, and nothing found; missing the `.codex` branch, and the fall-through test is the one that will catch the P0. **Manifests** — structure covered, matcher value not; `claude plugin validate` only opportunistically. **Installer refusal** — covered, but it breaks eight sibling tests (P1 #4). **Version bump** — covered except `package-lock.json`. **Hand-offs** — covered by regex, which is the right granularity here. Untested helpers: `lockedVersion()`, `vendoredSdkUrl`'s `module`/`main` branches, `claudePluginList()`'s throw path.

### 4. Performance

Nothing on a hot path; this is a packaging plan. Two things it makes measurably worse. First, `pluginInstalled()` spawns the real `claude` CLI on **every** `node scripts/install.mjs` run, including the eight installer spawns in the suite, adding a CLI cold start per spawn — cheap in absolute terms but paid on every `make install` and every test run; caching is pointless here, but the suite should be using the fake bin anyway for correctness (P1 #4). Second, the plugin payload grows: the repo's tracked files are 956 KB today (`vendor/` 228 K, `docs/` 220 K, `skills/` 252 K) and `vendor-node/` adds ~204 KB including two ~53 KB source maps, so `claude plugin update` pulls ~1.2 MB per version — within the spec's stated budget, and the maps could be dropped from the vendored copy if it ever matters. No N+1 patterns, no unbounded loops (the locator loop is three fixed candidates), no memory growth, no chatty external calls introduced.
