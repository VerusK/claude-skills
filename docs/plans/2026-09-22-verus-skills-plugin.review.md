## Section notes

### 1. Architecture

The shape is unchanged from round 1 and still right: the root is derived from `import.meta.url` in both installs, the hook is the only component that gets `CLAUDE_PLUGIN_ROOT`, and the pointer file is a one-way, best-effort channel with the symlink branches as fallback. The locator — the single point of failure — is now correct; I re-ran it against a real symlink tree and it returns the repo root. The new trust edge (`vendor-node/` as committed third-party executable code) is now guarded: `assertIntegrity` compares the packed tarball against the lock's `sha512-IddX+Q0...` before extraction, and Task 1 Step 4 runs the script, so a mismatch shows up in the task that introduces it rather than at some later release. `npm` here is 11.4.2, where `npm pack --json` reports the on-disk filename for a scoped package, so the `JSON.parse(out)[0].filename` read is safe. Two production failures the plan still does not name. First, the Codex leg of mutual exclusion (finding 1): `claude plugin list` cannot see a Codex plugin install, so the two installs can coexist there with duplicate skills. Second, pointer freshness: the pointer is refreshed on `startup|clear|compact|resume`, so a `claude plugin update` mid-session leaves it pointing into a removed `<version>` cache directory; under a plugin install there are no symlink branches to fall through to, and the plan degrades correctly (empty `SKILLS_REPO` → `distro root not found` → the skill asks the user) but never says so out loud. Build/publish for every new artifact is covered by `make release` + `claude plugin tag` + the documented push. No diagram needed; the spec's §4.3 flow is accurate and the plan's Architecture paragraph reproduces it.

### 2. Code quality

Module organization follows the repo's conventions throughout (ESM, exported pure functions plus a guarded `main()`, the `process.argv[1]` self-check, `mkdtempSync` + `after()`), and every anchor string the plan quotes was checked verbatim in its source file: `skills/kickoff/SKILL.md:66,75`, `skills/writing-plans/SKILL.md:173`, `skills/subagent-driven-development/SKILL.md:417,418`, `skills/review/SKILL.md:219`, `README.md:5,79,151` and the `ARGS` block, `USING.md`'s opening paragraph, and the `spawnSync(process.execPath, [SESSION_START], { encoding: "utf8" })` line at `tests/install.test.mjs:403`. Two of them (SDD item 2, review's line 219) are prefixes of longer lines, which the plan words as "replace the opening of" — an implementer doing a literal whole-line match would fail there, so the prefix wording matters. `skills/kickoff`, `skills/plan-review` and `skills/review` are indeed absent from `sources.yaml`, so Task 3's "no repatch needed" is correct, and `writing-plans` and `subagent-driven-development` are both `patch: true`, so Task 7 Step 10 is required. `vendor-node/` does not collide with `.gitignore`'s `node_modules/` and `scripts/sync.mjs` only ever walks `vendor/`, so the new directory is inert to the sync tooling — and Task 8 Step 5 documents it in CLAUDE.md. The remaining quality points are the three distro predicates (finding 5), the half-correct uninstall advice (finding 2), the dead `make test` target (finding 3), and two doc artifacts left behind: the judge.md "Act on the result" bullet and the SDD DOT diagram.

### 3. Tests

Framework and idioms are detected correctly (`node --test tests/*.test.mjs` via `npm test`, `node:assert/strict`, `mkdtempSync` + `after()`, `tests/fixtures/fake-bin` stubs); the existing 107 count is exact. I executed the three tests round 1 said could not work: `loadSdk` against a `vendor-node/`-only root returns `function` at status 0, the judge with a dummy key exits 2 with `judge failed:` offline, and `vendoredSdkUrl` throws `no ESM entry` on a package.json with no entry — all three now exercise real behaviour rather than short-circuiting. The locator suite's `extractLocator` regex (`/SKILLS_REPO=""\n(?:.*\n)*?done\n/`) matches the planned snippet in all three files, the `replaceAll` substitutions reduce the three to one identical block (the 9-space continuation indent is what makes that equality hold — keep it), and `SKILLS_REPO=""` occurs exactly twice in `judge.md`, so the second test is meaningful. Task 6's fake `claude` stub is consistent with the existing `codex`/`orca` stubs and does not perturb any other assertion in `tests/install.test.mjs`. Gaps that remain: the `$HOME/.codex/skills/<name>` locator branch, `vendoredSdkUrl`'s `module`/`main` shapes, `claudePluginList()`'s throw path, the Codex side of the mutual-exclusion check (finding 1 — the concrete test to add is `pluginInstalled refuses when ~/.codex/config.toml declares the plugin`, input a sandbox `$HOME` holding a `config.toml` with `[plugins."verus-skills@verus-skills"]`, expected `true`), and the whitespace-only pointer file. None of these is load-bearing for the plan to work.

### 4. Performance

Nothing on a hot path; this is a packaging plan, and the round-1 concern about `pluginInstalled()` spawning the real `claude` CLI in eight test spawns is gone now that they go through the stub. The one remaining cost is one extra CLI cold start per real `node scripts/install.mjs` run, which is correct behaviour and not worth caching. The plugin payload is unchanged from round 1: the repo's tracked files plus ~204 KB of `vendor-node/` (including two ~53 KB source maps that could be dropped from the vendored copy if the cache size ever matters), so `claude plugin update` pulls roughly 1.2 MB per version — inside the spec's stated budget. The SessionStart hook adds one `node` start, one 20-byte write and one small read per session, under a 10-second timeout. No N+1 patterns, no unbounded loops (the locator is three fixed candidates), no memory growth, no chatty external calls introduced.
