# Plan review: spec-review Implementation Plan
## Verdict
NEEDS CHANGES — the plan leaves common input and approval paths broken and relies on text checks for the core workflow.
## Findings (confidence 7+)
[P1] (confidence: 9/10) Task 1, §6 Hand off (.context/plan-review-prompt.md:378) — A user can request substantive changes after the external review, then approve a different spec because the plan expressly forbids another review; this defeats the goal of reviewing the spec before approval — rerun the reviewer on the revised spec before approval when the change affects requirements or design, or ask the user to acknowledge that the changed spec has not been reviewed.
[P1] (confidence: 9/10) Task 1, §0 Inputs (.context/plan-review-prompt.md:273-274) — `SPEC` accepts a path argument but derives `REPORT` from it while requiring a repo-relative output; an absolute spec path produces an absolute report path that `scripts/reviewer.sh:48-49` rejects — resolve the spec against the target repository, reject paths outside it, and derive a normalized repo-relative `REPORT`; cover absolute, relative, and missing paths.
[P1] (confidence: 9/10) Task 1, §4 Revise the spec and Acceptance (.context/plan-review-prompt.md:344-353) — §4 unconditionally appends an empty decisions section and runs `git commit -am` even when the review is CLEAR or every finding is left as is, while Acceptance expects no spec change on CLEAR; the commit then fails with nothing to commit or creates meaningless churn — append and commit only when there is a decision to record or an actual spec edit, and test the CLEAR path.
[P1] (confidence: 9/10) Task 1, §2 Launch the external reviewer (.context/plan-review-prompt.md:315) — exit 0 is treated as a complete report, but the unchanged `scripts/reviewer.sh:243-249` accepts any nonempty Codex report, including one truncated before `<!-- end of review -->`; the skill could parse partial findings and ask for approval — validate the final marker and required headings after every reviewer path before triage, then retry or stop on an incomplete report.
[P1] (confidence: 8/10) Task 1 tests and Acceptance (.context/plan-review-prompt.md:141-194, 775-779) — the proposed `node:test` checks match skill prose, and the single manual run covers only one happy path; none exercises the five Review Focus behaviors as actual input/output, so the skill can pass while launching without a spec, sending a `user` decision to the judge, breaking a seven-backtick fence, or handing off after a change request — add focused scenario checks with a temporary repo and fake reviewer/judge (or scripted manual checks where skill execution cannot be automated): for each named input assert the reviewer calls, prompt bytes, user question, spec/report content, and absence or presence of the `writing-plans` hand-off.
[P2] (confidence: 9/10) Task 4, README edits (.context/plan-review-prompt.md:697-737) — the planned replacements leave `README.md:12` saying the plugin ships ten skills, `README.md:24-25` saying only plans and branches get a second voice, and `README.md:110` omitting spec review from reviewer callers — update those prose lines and add assertions so the published install and workflow description stays accurate.

## Section notes
### 1. Architecture
The linear hand-off and reuse of the launcher and judge are coherent. The input normalization, report-completeness, and post-review change paths above are production failures at the new integration boundaries. The existing README diagram is updated; no additional plan diagram is needed. Version release is explicitly deferred in the spec, and plugin/install metadata is covered by Task 4.
### 2. Code quality
The new skill copies much of `plan-review` orchestration and its failure handling, so both can drift; keep duplicated blocks explicitly aligned or extract only the shared instructions that can be reused without weakening the skill boundary. Handle a CLEAR report without an empty decisions section or failed commit, and update all touched README prose.
### 3. Tests
The repo uses Node.js `node:test` through `npm test`. The planned tests cover frontmatter, routing strings, dispatch strings, report headings, and documentation, but do not exercise prompt construction, reviewer exit codes and incomplete output, user-decision triage, round-two preservation, or the approval gate. Add the concrete behavior cases in the findings; include a no-Decisions spec and a seven-backtick spec with expected report text and fence length.
### 4. Performance
No issues found. The new review runs outside a hot path, bounds source-file references at 40, and limits external review to two rounds with a 15-minute launcher timeout per round.
